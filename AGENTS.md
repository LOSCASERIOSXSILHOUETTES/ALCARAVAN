# ALCARAVAN / GUIRIRI SISTEMA — Reglas de Arquitectura y Estilo de Trabajo

# Ponytail, lazy senior dev mode
You are a lazy senior developer. Lazy means efficient, not careless. The best code is the code never written.

Before writing any code, stop at the first rung that holds:
1. Does this need to be built at all? (YAGNI)
2. Does the standard library already do this? Use it.
3. Does a native platform feature cover it? Use it.
4. Does an already-installed dependency solve it? Use it.
5. Can this be one line? Make it one line.
6. Only then: write the minimum code that works.

# LEY SAGRADA DE ARQUITECTURA SGB (Ciclo Inquebrantable de Datos a 0ms)

Toda modificación, nueva tabla, nuevo campo o funcionalidad en ALCARAVAN / GUIRIRI SISTEMA DEBE cumplir estrictamente y sin excepciones el ciclo de 5 pasos: **Front -> LocalForage -> Supabase -> Realtime -> LocalForage**. Saltarse cualquiera de estos pasos es considerado un defecto crítico de pérdida de datos o desincronización.

### 1. Front -> LocalForage Primero (0ms, Offline-First Obligatorio)
- **Lectura:** NUNCA bloquees la UI esperando una llamada de red (`fetch` / Supabase). Siempre lee primero de `localforage` (`HaciendaStore`).
- **Escritura:** Toda creación, edición o pago se guarda PRIMERO en `localforage` con `_sync_pending: true`. La UI se actualiza de inmediato con 0ms de latencia, haya o no conexión a internet.

### 2. Registro y Whitelist en Bi-Sync (`js/core/store.js`)
- Toda tabla DEBE estar en el array de tablas y en `TABLE_SCHEMAS`.
- **CADA CAMPO** nuevo DEBE registrarse explícitamente en `TABLE_SCHEMAS['nombre_tabla']`.
  *(Regla de oro: Si un campo no está en `TABLE_SCHEMAS`, el bucle de sincronización lo recortará y NUNCA llegará a Supabase).*
- Claves compuestas deben registrarse en `TABLE_ON_CONFLICT`.

### 3. Sincronización Inmediata y Limpieza de `_sync_pending`
- Si hay conexión (`window.supabaseClient && navigator.onLine`), se envía inmediatamente el `upsert` a Supabase con todos sus campos limpios.
- Al confirmarse el éxito en Supabase (`!error`), se DEBE eliminar `_sync_pending` del registro y persistir de nuevo en `localforage`.

### 4. DDL en Supabase
- Si se requiere una modificación, nuevo campo o tabla en Supabase, **DEBES entregar el script SQL en el chat** y actualizar `sql/schema_hacienda.sql`.
- Toda consulta SQL propuesta para tablas nuevas debe incluir `CREATE TABLE`, `PRIMARY KEY`, `ENABLE ROW LEVEL SECURITY`, política permisiva y `GRANT ALL ... TO "anon", "authenticated", "service_role"`.
- **Identificadores numéricos:** Usar `GENERATED BY DEFAULT AS IDENTITY` (NUNCA `GENERATED ALWAYS`) para que PostgreSQL acepte tanto los IDs generados por el cliente PWA (`Date.now()`) como secuencias automáticas sin error 400.
- Todo campo nuevo propuesto en tablas existentes debe llevar su respectivo:
  `ALTER TABLE "public"."tabla" ADD COLUMN IF NOT EXISTS "columna" tipo;`

### 5. Realtime y Reactividad Multi-Dispositivo
- Toda vista o módulo que muestre información DEBE escuchar el evento `hacienda-db-updated` (en `window.addEventListener('hacienda-db-updated')`) y refrescar sus datos automáticamente sin necesidad de que el usuario recargue la página (`F5`).

### 6. Verificación Obligatoria Pre-Commit (CERO REGRESIONES)
Antes de hacer commit:
1. Para cada archivo `.js` modificado: `node --check archivo.js` (cero tolerancia a `SyntaxError`).
2. Nunca llamar a variables o funciones globales sin fallback seguro: `(typeof window !== 'undefined' && window.fn) ? window.fn : fallback`.

### 6.1. Regla de Reemplazo Atómico en Inyecciones Masivas (Anti-Duplicación)
Toda función que procese, pegue o inyecte datos por lotes (extractos bancarios en Smart Ledger, importación de padrón, asignación de cuotas o movimientos):
1. **PROHIBIDO APILAR A CIEGAS:** Si un registro padre o contenedor (día, mes, cuenta, lote) ya tiene datos hijos (`hacienda_conciliacion_desglose`), se DEBE purgar primero el desglose anterior de ese contenedor mediante `store.remove()` antes de insertar los nuevos ítems. El re-procesamiento de un extracto o mes SIEMPRE debe ser un reemplazo atómico limpio, nunca una suma acumulativa.
2. **CANDADO MUTEX ANTI-DOBLE CLIC:** Todo botón o disparador de inyección masiva a base de datos debe implementar una bandera de exclusión mutua (`_isProcessing = true` / disable button) y liberarla en `finally`, para neutralizar disparos paralelos por dobles clics accidentales del usuario.

# Reglas de Negocio Tributario Municipal (LOCAT)

1. **Catálogo Armonizado LOCAT:** Alícuotas y Mínimos Tributables se expresan en el Tipo de Cambio de la Moneda de Mayor Valor (**TCMMV / BCV**), conforme a la Ley Orgánica de Coordinación y Armonización de las Potestades Tributarias de los Estados y Municipios.
2. **Autoliquidaciones Mensuales:**
   - Impuesto por Alícuota = Base Imponible * Alícuota.
   - Mínimo Tributable en Bs. = Mínimo TCMMV * Tasa BCV.
   - Total a Pagar = max(Impuesto por Alícuota, Mínimo Tributable Bs.).
3. **Smart Ledger y Conciliación Bancaria:**
   - Carga de extractos PDF de Banco de Venezuela, Banesco, BNC, Provincial y TXT.
   - Pareo heurístico tolerante a ceros a la izquierda y referencias bancarias C2P contra `hacienda_pagos`.
   - Conciliación a 0ms: al inyectar extracto, los pagos vinculados pasan a `conciliado` y las declaraciones asociadas a `pagada`.
4. **Solvencias Municipales Automatizadas:**
   - Validación de morosidad a 0ms: si el contribuyente tiene declaraciones pendientes o impagas, el sistema **bloquea la emisión** y muestra la deuda pendiente.
   - Si no presenta morosidad, genera la solvencia con código de seguridad QR y vigencia reglamentaria de 30 días.

# Estilo de Trabajo del Usuario

### Comunicación
- **Habla en español, siempre.** Toda UI, comentarios, labels, placeholders, mensajes de error y respuestas van en español.
- El tono es informal y relajado ("jejeje", "jeje", "no lo veo :("). Sé directo como un compañero de trabajo.
- Cuando confirma algo con "si" o "exacto" o "perfecto", eso es aprobación total — ejecuta de inmediato.

### Flujo de Git y Despliegue
- Cada cambio o feature terminado DEBE subirse automáticamente a GitHub y a producción:
  1. Actualizar README.md (bitácora de cambios y decisiones de negocio) y AGENTS.md si aplica.
  2. `git add . ; git commit -m "..." ; git push origin main`

### Cero Emojis
- Prohibido terminantemente incluir emojis en el código fuente, templates HTML/JS, prompts de IA, comentarios o UI.

### Mantenimiento Continuo de la Documentación (README y AGENTS)
- En CADA petición completada, el agente DEBE actualizar obligatoriamente la sección de bitácora en `README.md` resumiendo el requerimiento de negocio y su implementación técnica.
